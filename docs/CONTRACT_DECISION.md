# 三项合同建议：待业务决定

本页是可审阅的口径对照，不改变现行 v3.5 合同、标准分或源码。审阅原文第三节明确将这些事项区分为合同讨论，要求确认后版本化修改。直接事实/工具修复不等待本页决定。

## 1. 模块名关键词

当前至少两个规范命名模块是模块化 3 分的硬门槛；其中 database 的 base 子串计入。对 APP-02 的真实四模块事实，仅把名字 database 视作 storage、保持依赖图/职责/构建边界字段不变，规则输出 **3→2**。这是输入敏感性试验，没有实际重命名或重跑构建。
建议：去掉特定英文关键词对最高档的硬门槛，保留 ≥3 个真实内聚模块、无环及构建/测试或 API 边界条件。名称可读性作为明确问题记录，不能靠加 core/app 前后缀获得分数。

| 仓 | 当前模块化 | 仅取消关键词门槛的对照 |
|---|---:|---:|
| APP-01 | 3 | 3 |
| APP-02 | 3 | 3 |
| APP-03 | 1 | 1 |
| APP-11 | 3 | 3 |
| APP-13 | 0 | 0 |
| APP-14 | 2 | 3 |
| APP-15 | 2 | 待重新取证：cohesive_module_count |

若旧规则已由命名门槛决定低档，现有事实可能只有内聚模块数量下界；取消该门槛后不得把未知补为 3。上述待取证项必须重新检查，而非自动提分。

## 2. 公开 deprecated API

APP-03 的旧 WindowInsets getter 是目前决定性风险。仅移除 has_non_compatible_api 信号后，现有事实缺少“两版本自动兼容验证”的决定值，规则正确返回待补证，不能直接把未知填成 8。若另行确认不存在这种验证，其条件性对照为 **3→8**。该试验没有实现替代调用，也不证明行为等价或全部 API 风险已解决。
建议：把“公开 deprecated 且在支持版本范围内有已核实的局部替换路径、无核心行为/权限/ABI 迁移阻断”与未隔离 private/vendor/reflection 分开。前者最多 8；要得 10 仍须满足无未解决风险及接口隔离/多版本验证条件。未知替换代价不能自动归入低风险，私有接口和核心绑定的现有封顶保持。

## 3. 平台实现者的指标含义

建议保留 FW 编译独立性/平台升级的现有原始指标，但明确将它解释为“脱离当前平台独立构建/迁移的能力”，不直接等同代码设计质量。报告应同时显示职责和 SOLID 分项，不能仅凭平台固有依赖给出“设计差”的结论。
如果希望从框架实现者的合理职责中排除平台内部依赖，那将改变测量对象、适用性和档位，需要单独定义 v3.6，而不是以文字说明暗中抬分。

可选择保持 v3.5（本轮只发布事实修正），或批准上述建议后制定 v3.6 并对全部受影响 APP/FW 叶统一重审。此处未改变维度数量/权重，也未把对照值写入 canonical。
精确输入变动和结果见 [contract-sensitivity.json](contract-sensitivity.json)。
